# swap · 虚拟设备工程规范（`buddy-sim`）

> `buddy-sim` 是换电柜协议的**规范性设备实现**，与 `buddy` 平级的独立 Maven 工程。
> 它不是 mock、不是测试脚手架、不是临时脚本：M3 的全部异常与一致性自证、压测、混沌、E2E 都挂在它身上。
> 上游依据：[`swap-protocol.md`](swap-protocol.md)（§6 上行校验链、§13 故障注入目录）、[`swap-order-fsm.md`](swap-order-fsm.md)（§6 异常矩阵）、[`swap-plan.md`](swap-plan.md)（§6 硬约束、§7 B1~B3）。

---

## 1. 定位与三层能力

| 层 | 内容 | 归属里程碑 | 是否永久资产 |
|---|---|---|---|
| **L0** | 手工点验脚本（起 1 台柜、看日志通不通） | 开发过程顺手 | 否，用完即弃，不进正式结构 |
| **L1** | 规范性设备实现：入网注册、连接、上报、收指令、回 ACK、**完整校验链**、柜内物理模型、`swap_result` 生成 | **M1**（与云侧同期） | 是 |
| **L2** | 故障注入与编排平台：FI-01..16 全量、场景 DSL、seed 可重复、HTTP 控制面、双端指标、千台规模 | **M3**（其中 FI-01/02/04/10/13 提前到 M1，因为是 M1/M2 的验收必需） | 是 |

**L1 与 L2 不是"完整版与简化版"的关系**：L1 的校验链若缺失（比如不实现验签、不实现重复指令重放），L2 的所有故障注入都测不出东西。故 L1 即规范实现，L2 只是叠加编排与规模能力。

**它必须存在的理由**：云侧是异步发起方，指令发出后结果由设备决定。**没有可信的独立设备端，云侧接口会按"永远成功"的形状长歪**——回调默认成功、异常路径写成不可达分支——等到真实对手方接入时接入层要重写。这是把设备端与云侧串行的最大代价，也是本项目选择双轨同步的唯一原因。

## 2. 为什么不放进 `buddy`（三条硬理由）

| 理由 | 说明 |
|---|---|
| **生产包纯净性** | 本工程的每一项能力（伪造报文、错签名、重放 nonce、假 ACK、假装门磁、断连重连）**合起来就是一个攻击工具**。留在 `src/main` 里会被打进生产 jar、被镜像带走、被 Trivy 扫出。独立产物是唯一干净解 |
| **依赖与生命周期隔离** | 它需要 MQTT **客户端**、场景 DSL、seed 随机、HTTP 控制面；云侧需要的是 broker **服务端**与持久化。同 pom 会让两侧构建互相拖累 |
| **必须是独立进程** | 压测/E2E/演示都要设备端能独立起、独立扩规模、可部署到另一台机器。放 `src/test` 做不到：test 类不进任何可执行产物，且会连带拖入 Spring 上下文、Flyway、H2——**模拟器本就不该知道云端怎么存数据** |

**但仍是同一个 git 仓库**。协议、状态机、云侧实现、模拟器、golden 样本、测试必须住在**同一个 commit** 里。分仓迟早出现"模拟器还是 v1.0、云端已 v1.1"，那种状态下的测试失败会被误归因为代码缺陷。协议演进的可信度依赖原子提交。

## 3. 零代码共享原则（故意重复实现，登记为加严项 B1）

本工程 **不依赖 `buddy` 的任何 Java 类**，包括自己重新实现一遍：信封解析、canonical JSON 序列化、HMAC-SHA256 签名与验签、msgId 去重表、seq 高水位、ULID 生成。

理由——**防同源错误互相掩盖**：

> 若 canonical JSON 序列化写错（例如嵌套 map 未递归排序），而模拟器复用云端同一个类，则两端"错得完全一致"，所有测试全绿，协议却是坏的。
> 只有两端各自独立实现、互发真实报文，这个错误才会在第一次握手炸出来。

这看着违反 DRY，但共享对象选错了：**该共享的是数据资产，不是代码。**

### 3.1 `protocol/` 共享资产（仓库根，只放数据）

```
protocol/
├── v1/
│   ├── envelope.schema.json        信封字段与必填约束（双端各自据此实现校验）
│   ├── commands.json               指令矩阵（cmd / 幂等 / 重试 / ttl / 错误码族）
│   ├── error-codes.json            错误码表
│   ├── topics.json                 主题规范与 ACL 规则
│   └── samples/                    ★ golden 报文样本（双端共同断言依据）
│       ├── cmd_open_slot.json      ├── cmd_reply_ok.json
│       ├── cmd_reply_expired.json  ├── cmd_reply_badgen.json
│       ├── evt_door_close.json     ├── evt_battery_detected.json
│       ├── evt_swap_result.json    ├── telemetry_batch.json
│       ├── attack_forged_sign.json ├── attack_replay.json
│       └── compat_unknown_field.json  （v1.1 带未知字段，必须被忽略而非报错）
└── CHANGELOG.md                    协议样本变更记录（与协议文档同步）
```

- 两端各自**读同一份文件**做断言；读文件不构成编译期耦合。
- 新增/修改样本必须与协议文档、FSM 迁移表同一 commit 提交（M0-5 的文档自洽性契约测试会把这条变成机器约束）。

## 4. 工程形态

```
buddy-sim/
├── pom.xml                         com.lrs:buddy-device-sim，finalName=buddy-sim，独立可执行 jar
├── src/main/java/com/lrs/sim/
│   ├── SimApplication.java         独立 main（不引 Spring，杜绝任何 buddy 依赖渗入）
│   ├── protocol/                   自实现：信封 / canonical JSON / 验签 / ULID / seq / 去重
│   ├── device/
│   │   ├── CabinetDevice.java      柜机：N 仓位、门磁、电控锁、烟感/水浸/震动、柜温、漏保
│   │   ├── SlotModel.java          仓位：门态、锁态、有无电池、充电器态、充电功率
│   │   ├── BatteryModel.java       电池：SOC / SOH / 单体电压 / 温度 / 故障码 / 循环 / 位置
│   │   └── PhysicsClock.java       可控时钟 + SOC 爬升等状态推进（★ 参数化，不做热/机/电仿真）
│   ├── behavior/                   §6 校验链实现 + 指令执行 + 事件生成 + swap_result 组装
│   ├── fault/                      FI-01..16 各一实现 + FaultInjector 编排入口
│   ├── scenario/                   YAML 场景加载、seed 随机、规模与节拍定义
│   ├── control/                    HTTP 控制面（§8）
│   └── report/                     自身指标与结论输出（§9）
├── src/main/resources/scenarios/   *.yaml
└── src/test/java/…                 模拟器自身测试（§11，强制）
```

**技术栈**：Java 17 + **Vert.x**（非阻塞 MQTT 客户端 + HTTP 控制面 + 定时器 + Context 传播），**不引 Spring**。
选 Vert.x 的理由：① 一个依赖解决三件事，依赖面最小；② 非阻塞事件循环模型天然支撑"单 JVM 数千连接"，线程池模型会先撞线程上限；③ 与云端候选 broker（Vert.x MQTT Server）同生态。
**代价如实登记**：Vert.x 的回调/`Future` 风格与云侧 Spring 同步风格不同，读代码时要切换心智；因此 §11 要求模拟器自身有测试覆盖，不能靠"反正不是业务代码"过关。

## 5. 设备内部模型（仿什么、不仿什么）

| 仿（协议与状态语义） | **不仿**（物理效应） |
|---|---|
| 门开/关/故障三态及其事件序列与时间戳 | 电机堵转的电流曲线 |
| 电控锁吸合失败、门磁接触抖动（按注入参数产生） | 抖动的真实频谱与机械寿命 |
| 仓内有/无电池、电池码、SOC、电压、温度（**均为注入量**） | 温度随充电时长的真实变化、热失控时序 |
| 充电器启停、功率档位 | 功率器件效率与发热 |
| BMS 故障码、互锁状态、允许最大充放电电流 | 电芯老化机理、SOH 衰减真实曲线 |
| 4G 链路：延迟、丢包、断连、重连、NAT 静默中断（按注入参数） | 运营商网络的真实分布 |
| BMS 挑战应答签名（用测试密钥计算，可故意算错以测拒收） | 硬件安全芯片与密钥熔丝 |

> **正确性边界声明（必须随交付物存在）**
> 本工程验证的命题是：**给定这些输入，云侧输出是否符合规范**——即"系统对世界的假设是否自洽"。
> 它**不验证**"这些输入在物理世界是否真的会出现"，也**不构成任何物理安全性证明**。
> 温度、SOC、故障码是脚本注入的量，不由充电时长或环境推导。任何"我们证明了电池不会热"的表述都是错误的。

### 5.1 云端永远无法自证的部分（诚实边界，与 `swap-plan.md` §6 对齐）

| 无法自证 | 可测的替代命题 |
|---|---|
| 真实 4G 弱网特性（延迟分布、NAT 超时、断连频率） | 制造"长连接静默 8 分钟后恢复"，断言云侧不误判在线、旧会话应答被丢弃、过期指令被拒 |
| Broker 在真实连接数下的表现（1 万/10 万长连接、TLS 握手风暴、内存） | 千台规模 + 可外推资源模型；集群表现登记为需生产环境实证 |
| 时序库真实写入吞吐与压缩率 | 只测端口契约与降级路径 |
| 设备固件行为与硬件故障模式 | 只约定协议层："收到什么码做什么事" |
| 支付网络与银行侧真实时序 | 模拟渠道触发等价故障，测回调幂等与对账差异 |

## 6. 校验链实现要求（L1 即必须完整）

严格按 `swap-protocol.md` §6 的 10 步顺序实现，**任何一步不得省略或降级为日志**：

```
解析 → 主版本 → cmd 已知(禁止静默忽略) → 验签 → 有效期(brokerTs) → nonce 防重放
     → seq 单调(窗口内可容忍，缺口必须上报) → msgId 去重 → 前置状态守卫 → 执行
```

两条最容易被偷懒、但偷懒即导致 L2 全盘失效的实现点：

1. **重复指令必须"重放上次执行结果"**，不是"直接 return 不响应"。
   设备侧持久化 `(msgId → code, data, processedAt)`（保留最近 N 条 / 7 天），重复到达时原样重发应答。
   否则云侧拿不到应答会误判 `TIMEOUT`，把一次本来成功的动作搅成糊账，且**该项故障测试本身变成假的**。
2. **有效期判定不信自己的 RTC**，用投递时注入的可信 `brokerTs`；无 `brokerTs` 时对非幂等指令**保守拒绝执行**并上报。

**密钥来源**：设备 secret 不写死在场景文件里，由 §10 的入网注册流程从云端取得——这顺带成为对云端"设备开通链路"的真实验证。

## 7. 故障注入规范

FI-01..16 的**语义定义在 `swap-protocol.md` §13**（协议层规范，不因实现分期而删），本节定**实现要求**。

### 7.1 三项必备能力（缺一项则故障注入不可信）

| 能力 | 要求 |
|---|---|
| **精确编排** | 故障可绑定到"订单第几步之后 + 相对延迟"（例：`afterStep=S4, delay=2.3s`）或"第 N 条报文上"或"绝对时刻"。**不可只用百分比概率**——概率注入无法做回归断言 |
| **可重复** | 每场景一个 `seed`，全部随机（延迟、乱序、丢包、值噪声）由该 seed 派生。同 seed 重跑必须产生**同一事件序列**，否则 CI 红绿不可解释 |
| **可观测** | 每次注入落一条结构化记录（时间、目标设备、FI 编号、参数、设备侧实际动作），供 §9 归因与 M3 故障矩阵报告引用 |

### 7.2 关键实现提示（几条不写清就会被做错的）

- **FI-04（ACK 成功但事实事件不来）**：必须真的"已执行物理动作、只是不上报"，而不是"什么都没做"。否则测的不是 `UNCONFIRMED`，而是白名单内的正常超时。
- **FI-10（重连 + 旧会话迟到应答）**：要真的先把报文扣在设备侧队列、完成重连、再按旧 `sessionId` 发出。仅改 `sessionId` 字段测不到云侧的会话隔离分支。
- **FI-13（取走电池门未关）**：`battery_taken` 必须正常上报（B1 口径要扣钱），门未关走独立告警。这条的断言点是"订单照常完成 + 柜侧异常告警"两件事同时成立。
- **FI-14（安全联动分岔）**：需要能在 `S3 之后`与`S5 之后`两个位置各触发一次，因为云侧结论相反。缺一个位置，双分岔等于没测。
- **攻击类（FI-07/08）**：必须走完整连接流程后再发非法报文（不是伪造连接），这样才测得到云侧与设备侧**两层**分别的拒绝路径。

### 7.3 场景 DSL（M3 阶段 2 已交付）

场景文件是唯一存放处：仓库根 `protocol/scenarios/*.json`（共享数据资产，**不往 `src/main/resources` 复一份**，
复一份就会一份改一份不改）。入口：`java -jar buddy-sim.jar --scenario fi05-out-of-order [--host … --port …]`，
退出码 0/1，失败时逐行报“期望 vs 实际”；`--list-scenarios` 列出全部。

| 步骤 | 字段 | 语义 |
|---|---|---|
| `fault` | `kind` / `cmdCode` / `repeatTimes` / `errorCode` / `times` / `value` | 追加一个触发器（实现 §7.1 的“精确编排”，参数为空则报错而不是猜默认值） |
| `send` | `cmd` / `data` / `ttl` / `critical` | 云侧替身下发一条指令（`critical` 走 `cmd/critical`） |
| `sendExpired` / `sendBadSign` / `sendReplayNonce` / `resend` | `cmd` / `data` | 异常报文四种形态：发出即过期 / 错签 / 旧 nonce+新 msgId / 同 msgId 重投（后两个是 FI-07 与 FI-02，形状不同所以分两个动词） |
| `action` | `action=insert\|take\|close\|telemetry\|alarm` | 代用户执行物理动作（投入与关门是两个事实） |
| `link` | `op=connect\|disconnect\|reconnect` | 连接生命周期（FI-10 与混沌用） |
| `wait` | `ms` | 时间推进 |
| `assert` | `cmd` / `replyCode` / `replyCount` / `anyReplyCode` / `events` / `absentEvents` / `eventCounts` / `order` / `faultFired` / `rejectedInboundAtLeast` / `settleMs` | 设备侧行为形状断言 |
| `log` | `message` | 报告行 |

**只做线性步骤，不做分支与循环**（计划风险 R4）：一旦出现“需要 if”，拆成两个场景文件或回到测试代码，
不给这个格式加语法。需要跨报文比对字段（如“应答的 sessionId 等于重连前那个”）的断言留在代码里
（`SimFiMatrixTest#staleSessionReplyCarriesOldSessionId`）。

矩阵用例：`SimFiMatrixTest` 把 `protocol/scenarios/` 下**每一份文件**当一条用例跑，另外两条固化的断言：
① **FI-01..15 每项至少一份场景**（文件被删就会红，而不是静默变少）；② **同 seed 跑两次到达顺序一致**。

### 7.4 千台规模（M3 阶段 2 已交付，口径先说清）

`SimScaleTest` 证的是**同一个 JVM 内 1000 条设备连接**：建连、每台一条遥测、抽样 20 台做真实指令往返、
全部释放后 `isConnected()` 必为 false（不拿“没报错”当“已释放”）。本机实测：**4.7s、堆增量 42 MB**。
**不证** 1000 台真机 / 1000 个进程 / 跨机网络 / Broker 集群容量（属外部硬约束，最接近的替代是 M7 互操作档）。
把结果写成“1000 台设备在线”就是谎报。

## 8. 控制面（HTTP）

### 8.1 已交付（M3 阶段 2，`--control-port <port>`）

实现在 `SimControlServer`（JDK `HttpServer`，不引 Web 依赖）。路径不带 `/sim` 前缀（单进程只服务自己那批设备，
前缀只是噪声）；多设备时**必须带 `?device=`**，只有一台时可省略——“给哪台注入”不能靠猜。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/status` | 会话号（含旧会话）、仓位快照（门/锁/充电）、已注入故障、已触发记录、五个计数器 |
| POST | `/fault` | 即时追加一个故障触发器（E2E 与手工演示用） |
| POST | `/action` | 代用户执行：`insert` / `take` / `close` / `telemetry` / `alarm` |
| POST | `/link` | `connect` / `disconnect` / `reconnect`（FI-10 与混沌场景的开关） |
| GET | `/metrics` | Prometheus 文本（见 §9） |

默认只绑 `127.0.0.1`；传 `--control-port 0` 由系统分配端口（测试靠它避免端口冲突）。
**没做鉴权**：这个进程能伪造报文、错签、重放，所以它只能出现在本机与 CI，
一旦需要对外暴露就必须先加 token（登记为未交付项，不默认存在）。

### 8.2 本节原本要求、但 **尚未交付** 的能力（诚实边界）

| 能力 | 状态 | 影响与替代 |
|---|---|---|
| `/sim/step/advance` 可控时钟推进 | 未做 | 场景靠 `wait` + 真实延迟；确定性由 seed 与 `settleMs` 保证，目测未出现不可解释的拖红 |
| `/sim/devices/{id}/claim`（设备主动声明） | 未做 | 云侧“用户声明不推进状态”的断言在 `SwapFlowService.declareClosed` 的单测里走 API 层测，不依赖模拟器 |
| `/sim/report/injections` | 未做（并入 `/status` 的 `faultFired`） | 注入记录目前只在进程内存里，**不落盘**：长跑归因需要报告时这里会不够用，已登记 ROADMAP §4 |
| `sim.control.enabled` 开关 | 未做 | 现阶段以“不传 `--control-port` 就不启”为等价实现 |

## 9. 双端可归因（加严项 B3）

模拟器暴露 Prometheus 指标，命名空间 `sim_*`：
`sim_connected_devices` / `sim_msg_sent_total{kind}` / `sim_msg_recv_total{kind}` /
`sim_reject_total{code}`（验签/过期/重放/未知 cmd/前置守卫各自计数）/
`sim_duplicate_cmd_replayed_total` / `sim_inject_total{fi}` / `sim_phys_state{device,slot,attr}`。

**归因矩阵**（这是它存在的唯一理由——没有它，压测结论无法解释）：

| 云侧观测 | 设备侧对应观测 | 结论 |
|---|---|---|
| `cmd` 超时 | 无 `msg_recv` 记录 | 报文未达（网络/Broker 侧） |
| `cmd` 超时 | 有 `msg_recv` + 已执行，但无 `sent cmd_reply` | 设备执行了、应答丢失 → **超时 ≠ 未发生**（FI-01） |
| `cmd` 超时 | 有 `reject_total{EXPIRED}` | 指令过期被拒，云侧重投逻辑有问题 |
| 事件"丢失" | `msg_sent_total` 有该事件 | 云侧消费/去重环节丢了，不是设备没报 |
| 状态与 `swap_result` 不一致 | `sim_phys_state` 为准 | 判定云侧投影错，还是设备陈述错 |

## 10. 入网注册流程（顺带验证云端的设备开通链路）

```
场景启动 → 按台账申请注册（deviceId + productKey + 租户）→ 云端下发 deviceSecret（一次性）
        → 派生 connSecret / msgSecret → 连接（HMAC 口令）→ session_ready 首报 → 纳入节拍
```

真实项目里"出厂 → 录入平台 → 绑定租户 → 首连"是一条独立且极易没测通的链路；本流程让它每次 CI 都被走一遍。
密钥在内存中不落场景文件，日志与错误输出禁止打印 secret 与完整 sign（与协议 §9 同规）。

## 11. 模拟器自身必须有测试（不许"反正不是业务代码"）

故障注入本身是坏的，则 M3 全部结论作废。故最低要求：

| 测试 | 断言 |
|---|---|
| `ProtocolSelfTest` | 逐条读 `protocol/v1/samples/*.json`，自身解析/签名/验签与 golden 一致 |
| `ValidationChainTest` | §6 十步各自的成功与拒绝路径（含"重复指令重放结果"） |
| `PhysicsModelTest` | 门/锁/仓位/电池状态机迁移合法（例如"门开着不能直接变锁定"） |
| `DeterminismTest` | 同 seed 重跑两次 → 注入记录与事件序列逐字节一致 |
| `ScaleSmokeTest` | 单机 1000 连接的启动/上报/断连重连不泄漏（堆与句柄） |

## 12. 分期与同步点

| 里程碑 | 设备侧交付 | 与云侧的同步点 |
|---|---|---|
| M0-3 | 工程骨架 + `protocol/` 目录与首批 golden 样本 + 场景 DSL schema | 与 DDL 枚举、指令矩阵同时定稿，由 M0-5 契约测试锁住 |
| M1 | **L1 完整体** + FI-01/02/04/10/13 + 入网注册 + `sim_*` 指标 | 云侧 broker 与指令总线的唯一对手方；golden 双端互解 + mosquitto 互操作 |
| M2 | 多柜多电池并发、事件时序、`swap_result` 生成 | 支撑 39 条迁移与主链路 E2E（H5 页面直接驱动它） |
| M3 | **L2 全套**：FI-01..16 补满、场景 DSL 完整、控制面、千台规模 | 16 项故障矩阵 + 混沌 + 压测（不变式违反数 = 0） |
| M4 | 支付回调故障编排（重复/乱序/验签失败/退款失败） | 回调幂等与对账差异测试 |
| M5 | 传感器时序注入、位置移动（围栏）、复核流程对侧响应 | 告警规则引擎与联动 E2E |
| M7 | 支持指向外部 broker（EMQX）的配置化切换 | 双 broker 同协议验证 |
| M8 | 二进制帧 codec 的设备侧实现 | 同一套 golden 样本双 codec 通过 |
| M9 | 证书校验与密钥轮转的设备侧响应 | 四类认证测试 |
